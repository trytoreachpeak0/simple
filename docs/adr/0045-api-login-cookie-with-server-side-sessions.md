# 服务端接口的登录：Cookie 加服务端记着的每一次登录，改密码、退出立刻生效

ADR 0016 定了控制台用共用的本地账号、登录不定时失效；ADR 0014 定了三级角色按动作分；ADR 0033 加了只能看的值守账号和"暂停值守"。可服务端接口到现在还没有登录，只在本机回环上听（仓库 `CLAUDE.md` 的 Safety 一节），控制台出不了 factory01，值守 AI 也看不到生产。这一篇定登录怎么做：账号和密码存在哪、登录状态怎么维持、每个接口怎么按角色卡住，以及控制台、MCP、值守 AI 和 `simple` 命令行各怎么登录。控制台在厂区网上怎么加密另见 ADR 0046。

这是纯技术题，按产品负责人的工作方式（2026-10-16），先调研几套方案、讲清现场后果，再由产品负责人挑（2026-10-17）。调研读的是 ASP.NET Core 10.0 的文档和 `release/10.0` 源码、OWASP 的密码存储与会话管理两份 Cheat Sheet、NIST SP 800-63B-4、RFC 10017（浏览器应用的最佳实践，2026 年 8 月），以及 Chromium 的源码和官方说明。

## 决定

- **登录状态由服务端记着**（产品负责人 2026-10-17）：登录成功后浏览器里只放一个随机的登录凭条（加密的 Cookie）；服务端数据库里每一次登录是一行登录记录：哪个账号、经哪个入口（控制台、MCP）、从哪台电脑（IP 地址）、什么时候登录、最后一次来是什么时候。每个请求服务端都核对这一行；核对用内存里的那份，数据库短暂连不上时不把人踢出去。
  - **改密码、删账号：这个账号在所有电脑上的登录立刻作废**（产品负责人 2026-10-17 确认接受）。有人离开、管理员改了共用账号的密码（ADR 0016），他电脑上开着的控制台当场失效；同时，车间里开着看告警的那些控制台也一起回到登录页，要用新密码重新登录。
  - **在一台电脑上点"退出"，服务端删掉那一行登录记录**，那张凭条即使被复制走也不能再用。
  - **服务端重启不掉登录**：登录记录和加密凭条用的钥匙都存在数据库里，钥匙另加保护。网络断了再恢复也不用重新登录（ADR 0030）。
  - **超过 400 天没来过的登录记录由服务端清掉**：那样的凭条浏览器也早已不再带（见"'不超时'在技术上意味着什么"），留着只会越积越多。
- **登录 Cookie 的属性**：一律 `Secure`（只走 HTTPS）、`HttpOnly`（网页脚本读不到）、`SameSite=Strict`（只在本站发出），名字带 `__Host-` 前缀（RFC 10017 §6.1.3.2 对 `Secure` 是必须）。它是持久 Cookie，关浏览器、关电脑都不掉。浏览器带 Cookie 只看主机名、不分端口，`Secure` 保证它不会从同一台机器上的明文地址（ADR 0046 的车辆一览页）发出去。本机回环上走明文的开发、测试和 `simple` 命令行怎么带凭条，由实现票定。
- **防跨站伪造请求**（别的网页借着已登录的浏览器偷偷发请求）：除了 `SameSite=Strict`，改东西的请求必须带一个自定义请求头；服务端不开跨域访问（CORS），别的网站就发不出带这个头的请求。这是 OWASP 和 RFC 10017 推荐的组合。ASP.NET Core 的 Minimal API 只对表单端点自动做防伪校验，JSON 接口要自己守这一条。
- **账号和密码**存在服务端自己的 SQL Server 库里（`Simple_<instance>`，EF Core 迁移），不另起数据库。密码只存哈希：用框架自带的密码哈希（PBKDF2-HMAC-SHA512，加盐），运算次数调到 OWASP 现行推荐的 22 万次（框架默认 10 万次，产品负责人 2026-10-17）；旧哈希在下次登录时自动升级。密码本身哪里都不存，也不进程序日志（ADR 0034 的脱敏）。
- **账号表另存一列"最后一次来"**：每次核对登录时顺带更新，退出或删掉登录记录时不清。值守 AI"最后一次来看的时间"（ADR 0033）就是值守账号这一列；值守 AI 每次跑完就退出，它的登录记录留不住。
- **密码规则只有一条：至少 8 个字符**（产品负责人 2026-10-17）。不要求大小写、数字、符号混搭，不定期强制改。NIST SP 800-63B-4 对"只靠密码登录"要求至少 15 个字符，产品负责人要简单；8 个字符更容易被猜，靠按电脑限速和"要登录的控制台只在固定几台电脑上用"（ADR 0046）兜底。
- **防猜密码：按电脑限速，不锁账号**（产品负责人 2026-10-17）。同一台电脑连续输错要等一会儿才能再试；不做"错几次锁账号"，账号是共用的，锁了整个车间都登录不了，谁都能故意这样捣乱。
- **每个接口默认关着**：没写明谁能用的接口一律要登录。不用登录的只有：登录接口、车辆一览页和它的数据（ADR 0016）、控制台的静态文件、"进程活着"的健康检查。
- **角色卡到每个接口**：ADR 0014 的动作表在代码里只写一处，每个接口标明最低角色（班组长、工程师、管理员），只读的接口标"看"或"看全部"（管理员和值守账号）；"只能动本项目的车"在接口里按业务核对（ADR 0015）。有一条测试枚举全部接口，哪个没标谁能用就失败。
- **值守账号**只过"看"的那几道；"暂停值守"开着时，它的每个请求包括登录都回"已暂停"（ADR 0033）。
- **程序和人用同一个登录**（产品负责人 2026-10-17）：MCP 和值守 AI 用账号名和密码走和控制台同一个登录接口；值守 AI 每次起来时登录、做完退出。
  - **经 MCP 的登录，服务端只放行看和改参数配置**（事件记录保存天数除外，ADR 0016，产品负责人 2026-10-17）：登录时说明入口，这次登录在服务端就被限在 MCP 的边界里，AI 拿着它直接调接口也按不了让车动的动作、管不了账号。入口是登录的一方自己报的，这条边界防的是误用，挡不住有意绕开的人：拿到管理员密码、自称从控制台登录，仍然什么都能做，这是 ADR 0016 已接受的代价，不变。
  - **`simple` 命令行**只管本机的测试系统（仓库 `CLAUDE.md`）：`simple up` 给新起的系统随机设一个管理员密码，存在克隆目录之外那个系统自己的文件夹里（`%LOCALAPPDATA%\simple\instances\<instance>\`，或 `SIMPLE_HOME` 下），命令行自己用它读状态和事件记录（产品负责人 2026-10-17）。
- **第一次装好时的管理员密码，以及管理员密码忘了的时候**，只能在服务端那台机器上运行一条服务端命令来设；网页和接口上没有这个入口（产品负责人 2026-10-17）。要能登录 factory01 的人才能重设管理员密码。这是仓库 `CLAUDE.md`"控制台能做一切控制，不用脚本、SSH"的一个有意的例外：网页上能重设管理员密码，就等于谁都能试着拿走最高权限。管理员记得旧密码时，在控制台的账号页上输入旧密码就能改自己的密码。
- **记在哪**：
  - 人的每个动作照旧进事件记录（ADR 0019），写账号和入口，**另加从哪台电脑（IP 地址）按的**（产品负责人 2026-10-17）：账号是共用的，这是追到"哪个工位"最近的线索；追溯到人仍靠排班（ADR 0016）。管账号的动作（建、删、改密码）也记，不记密码。
  - 登录、退出、登录失败记进程序日志（ADR 0034），写明哪台电脑，不进事件记录（产品负责人 2026-10-17）：事件记录只记系统的变化和人的动作，值守 AI 每 15 分钟登录一次，记进去一天就近两百条。值守 AI 读程序日志，看得到有人反复猜密码。

## "不超时"在技术上意味着什么

ADR 0016 定了登录不定时失效，这一篇不改它，只写清后果：

- OWASP 会话管理要求每个会话都有空闲超时和绝对超时，"不超时"不在它认可的选项里。ADR 0016 有意不满足，理由已写明。
- 一张被偷走的登录凭条，在那台电脑退出或这个账号改密码之前一直能用。服务端记着每一次登录、退出和改密码当场生效，是不超时的前提下能收得最紧的做法。
- Chrome 对一个 Cookie 最长只认 400 天。登录 Cookie 的有效期就设 400 天，每天第一次使用时由服务端续成新的 400 天（框架默认要过了一半才续，那样实际只有 200 天，所以要改）。于是"一直有效"实际是"这台电脑 400 天里打开过一次控制台就一直有效"；超过 400 天没打开过的，重新登录一次。

## 考虑过的做法

- **用 ASP.NET Core 自带的整套账号系统（Identity），浏览器里放写着账号和角色的加密 Cookie**：哈希、改密码、角色都现成。不选的原因：
  - 改密码后旧登录要等服务端下一次复核才失效，默认 30 分钟一次，调短了就和本篇一样每次核对；
  - 一台电脑点退出只删掉这台浏览器里的 Cookie，被复制走的那份仍有效；
  - 服务端不知道一个账号在几台电脑上登录着；
  - 它按"一人一号"设计，带着邮箱、手机号、双因子、外部登录等一堆用不上的表和概念；现成的接口 `MapIdentityApi` 带一个任何人都能调用的注册接口、没有退出接口，"连错 5 次锁 5 分钟"用在共用账号上会被人故意锁死，这些都要关掉或绕开。
- **令牌存在浏览器里，每个请求带上**：浏览器和程序用完全同一种方式，也不用防跨站伪造请求。不选的原因：浏览器里任何一段脚本都读得到令牌；控制台要用不少 npm 第三方包（ADR 0031），一个被投毒或页面被注入一段脚本，令牌就能被悄悄送出去，而且按"不超时"一直有效。RFC 10017 建议业务系统不要把令牌放在浏览器脚本里，用"服务端加 Cookie"；微软对同域的单页应用也建议用 Cookie。
- **接厂内 AD、用 Windows 账号登录**：ADR 0016 已否。
- **自己搭一套标准的登录服务（OpenID Connect）**：多一个要装、要维护的服务，几个共用账号用不上。
- **错几次锁账号**：见"防猜密码"。
- **密码至少 15 个字符**（NIST SP 800-63B-4 对只靠密码登录的要求）：更难猜；登录一次一直有效，平时很少输。产品负责人要更简单的规则，定为至少 8 个字符。
- **设置密码时查常见密码黑名单**（NIST SP 800-63B-4 同样要求）：能挡住 `12345678` 这类一猜就中的密码；按"只有一条规则"没有做，`12345678` 也能通过。
- **登录、退出也进事件记录**：值守 AI 每天近两百次登录会淹没事件记录。
- **值守 AI 最后一次来看的时间取它那几行登录记录**：值守 AI 每次跑完就退出、记录随之删掉，时间读不出来，所以另存在账号表上。

## 后果

- 要自己写的部分：账号表、登录记录表、登录和退出接口、每次请求的核对，估计几百行。按仓库规矩手写要说理由：框架没有自带服务端登录记录的存储（`ITicketStore` 只有接口，没有现成实现），Identity 管"一人一号"的那一套用不上；加密、密码哈希、按角色授权、限速这些安全上要紧的部分全用框架自带的。
- 加密凭条用的钥匙存进数据库并加保护。不处理的话，不在 IIS 里跑的服务端可能每次启动都换一把新钥匙，重启后所有人被踢回登录页。数据库搬到别的机器上恢复时，钥匙的保护解不开，所有人重新登录一次。
- 账号页上看得到每个账号此刻在几台电脑上登录着（只显示，不加按钮）。
- 仓库 `CLAUDE.md` Safety 一节"服务端接口有鉴权之前只听回环"的规则，由实现登录的票改写，改成什么见 ADR 0046；改仓库 `CLAUDE.md` 要产品负责人在那张票的窗口里亲自确认。在那之前现行规则照旧有效。
