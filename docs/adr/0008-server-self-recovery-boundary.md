# 服务端只自己做停下、重试和能读回证明的恢复，其余停下等人

服务端遇到异常时，只在三种情况下自己动手：往安全方向走、重试没有副作用的读取和连接、恢复它自己原本在做且能读回证明条件未变的事；其余一律停下、告警、等控制台的人。上一代系统把大约 45 种异常压在现场人员或工程师身上（在车载屏开会话、SSH 到服务器跑命令、改数据库），而服务端掌握的事实其实够它自己办或让控制台一键办；反过来，服务端也不能替人判断它分不清的事，例如一个锁是修好了还是碰巧读到一次锁闭。拿不准时停下等人，不能继续往下错。

## 决定

- 服务端自己动手的三种情况：
  1. **往安全方向走**：下三类急停（ADR 0009）、暂停移动单、停下一台车的仓位操作、停止往某台车或某个区域号派新任务。做错的代价只是少送一单，符合"宁漏不重"。这类动作**不设次数上限**：条件每出现一次就做一次。例如仓门没证明锁闭时有人反复让车走，服务端每次都要把车停下，不能因为停了很多次就不再停。
  2. **重试没有副作用的读取和连接**：读 MES、连车队调度系统、连车载终端、读 IO 模块。这类重试**一直进行、不放弃**，间隔逐步拉长到一个上限；持续超过一段时间仍未恢复就告警，告警后照样重试。
  3. **恢复它自己原本在做的事，且能读回证明条件和之前一样**：例如我们的移动单被人在车队调度系统网页上误取消，在同一台车上重建。只有这一种有**刹车**：同一个问题在一段时间内反复需要自动恢复，或自动恢复失败，就停下交给人。时长、次数和计数单位由各条具体规则定。让车开始或恢复移动的恢复，还要先满足 ADR 0009 的门锁条件。
- 其余情况都停下、在控制台告警，等人决定。第 3 种自动恢复不了、停下交人的情况（刹车触发或恢复失败）都算故障，经故障处置收尾（ADR 0012），所以交人之后总有出口。
- 故障按服务端能不能自己看出已恢复来结束：

  | 故障 | 怎么结束 |
  | --- | --- |
  | MES 网关故障、MES 故障 | 服务端又读到正常数据，自动结束，留记录 |
  | 车队调度系统连不上、登录不了 | 又连上了，自动结束 |
  | 车队调度系统里地图或车辆被误删 | 人确认后结束：服务端看到地图或车辆回来了，但分不清是不是原来那个 |
  | 服务端对移动单或车的上线状态自动恢复不了（ADR 0010、0011） | 一律经故障处置，以处理好后继续或停用这台车结束 |
  | 配置故障 | 改好后服务端重新读取、校验通过，自动结束（与 ADR 0002 一致） |
  | 车载终端故障、IO 模块故障 | 重新连上后，车载终端上报全部门锁和光幕读数；与服务端记录一致就自动结束，不一致（例如断联期间仓里的货被取走或放进）转故障处置 |
  | 仓位故障 | 一律经故障处置，人确认才结束 |
  | 车辆本体故障 | 一律经故障处置：车长期离线后回来，期间可能被推走或修过，服务端不自行认定它没事 |

  服务端故障之后服务端怎么接着工作，不在本篇范围。

## 考虑过的做法

- **沿用上一代，异常多数停下等现场人员在车载屏处理**：现场人员负担重，远程的人什么都做不了，与"现场人员处理得越少越好"相反。
- **所有自动恢复统一设次数上限**：安全方向的动作不能因为做过很多次就停；网络重连也必须一直尝试。上限只适合"恢复自己原本在做的事"这一类，用来防止服务端在一个反复出问题的地方自己打转。
- **服务端更积极地自己判断，例如锁连续几次读到锁闭就认定已修好**：服务端分不清修好和偶然读数，判错了车会带着坏锁继续跑。
