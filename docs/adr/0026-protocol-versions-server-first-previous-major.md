# 协议版本：服务端先升级并兼容上一个大版本，同一大版本只加不改

上一代协议每条消息都带整个协议发布内容的哈希，两端必须逐字节同一个版本，接收方拒收任何多出来的字段，所以加一个显示字段也是破坏性的大版本：全产品线不到四周发了三个大版本，每次都要停下全部车、两端一起换，派生十几到二十几张票，再把门禁证据全部重跑一遍。

产品负责人定了现场怎么升级（2026-10-16）：平时先升服务端，车载终端再一台一台换，换一台时其余车照常干活；少数真正不兼容的大改动，才约一个停线窗口全部一起换。调研比较了三种版本做法（同一大版本只加不改；两端完全同版本加自动更新；两端互报支持哪些功能），产品负责人选了第一种（2026-10-16）。

## 决定

- 协议的大版本写在连接上。同一个大版本里只加可选的内容，不改、不删已有内容的含义；接收方忽略看不懂的新内容。删掉的字段编号永不再用。改名、改含义、删掉必须有的内容，都要开新的大版本。
- 服务端同时兼容当前和上一个大版本的车载终端，更旧的拒绝。旧的大版本在服务端保留到所有车的车载终端都升级为止；控制台上能看到每台车的车载终端是什么版本。
- 被拒绝的车载终端，车载屏单独显示"车载终端版本需要更新，请联系系统维护人员"，不并入"与服务端断开"，免得现场的人白白去查网络（产品负责人 2026-10-16）。控制台告警写明是哪台车、它是什么版本、服务端要求什么版本。服务端对这台车按断联处理（ADR 0009）。被拒绝后车载终端照常按逐步拉长的间隔重试，不形成重连风暴。
- 不再按协议内容的哈希绑定两端。

## 考虑过的做法

- **两端完全同一个版本，服务端升级时自动把车载终端推上去**：每次升级都要三台车同时能停下更新，自动更新出问题时一次发布能让全部车不能用；本质上是上一代"逐字节同版本"的老路。自动更新以后可以作为部署手段加在本篇之上，但不作为兼容的前提。
- **两端连接时互报支持哪些功能，服务端按每台车的功能分别处理**：新旧车能长期混跑，但现场会出现"这台车有某个按钮、那台没有"，服务端到处是按功能的分支，没有自然的清理时机。
- **沿用上一代按内容哈希绑定**：加一个显示字段就要全线停车升级、全量重测。

## 后果

- 日常升级不用停全部车。
- 给车载屏加按钮、加显示内容大多不碰协议（ADR 0024 的通用屏幕描述），真要动协议也多半只是加字段。
- 真正不兼容的改动要在服务端并行保留上一个大版本的处理，直到车载终端全部换完。
