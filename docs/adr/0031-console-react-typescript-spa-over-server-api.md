# 控制台用 React 加 TypeScript 的单页应用，只调服务端接口，由服务端进程提供

ADR 0016 定了控制台是网页、前端框架由实现控制台的票定。这一篇把框架定下来，因为它决定了控制台和服务端接口的关系、要不要第二套工具链，以及 Wi-Fi 抖动时是什么表现，这些都不好事后再改。这是纯技术题，按产品负责人的工作方式（2026-10-16），先调研几套方案、讲清现场后果，再由产品负责人挑（2026-10-17）。

控制台要做的事见 ADR 0029、0030：首页是一张可以拖动、缩放的地图，车每秒在动；点车、点机台显示详情；断线 2 秒按钮变灰、3 秒出红条，恢复后自动接上；按下的动作由服务端核对画面上看到的状态。约束是：控制台由服务端进程提供（仓库目录表：`src/Simple.Server.Console`）；AI 要能测，仓库的规矩是观察系统只有一个入口，即服务端的接口和事件记录；优先用成熟的库。

调研原本还有一条约束"尽量不引入第二套语言和工具链（例如 Node）"，产品负责人放开了：SIMPLE 可以引入（2026-10-17）。

## 决定

- **控制台是一个 React 加 TypeScript 的单页应用**，只调服务端接口，不另有专门给网页用的接口或页面片段。车和需求的"为什么"、每个动作能不能按和不能按的原因（ADR 0029、0030），都由服务端接口给出；控制台、MCP、AI 和测试看到的是同一份。
- **每秒向服务端接口取一次数据**（轮询），每次都是独立的一次请求。Wi-Fi 断 2 秒、30 秒还是 5 分钟，表现都一样：恢复后下一次请求就拿到最新数据，没有会话要恢复，不用刷新页面。请求要设超时（2 秒上下），免得 Wi-Fi 断了而连接没被正式关掉时请求一直挂着、后面的请求全排在它后面。
- **由服务端进程提供**：前端编译成静态文件，由服务端进程用和接口同一个地址提供，不单独起进程。仓库目录表里"控制台跑在服务端进程里"仍然成立。
- **用成熟的库，不手写框架**：组件库建议用 Ant Design（中文支持是原生的，按钮、确认框、表单、表格现成）；数据请求、地图的拖动和缩放也用现成的库。具体选哪些库，由实现控制台的票定，PR 里说明理由。
- **测试**：业务判断在服务端，主要打服务端接口来测；控制台本身用 Playwright 驱动真浏览器，测几条主线（例如点车、按停用、确认；断线时按钮变灰）。用 Playwright 的 .NET 包（跟着 xunit 和 `dotnet test` 跑）还是 Node 的 `@playwright/test`（跟着前端项目跑），由实现控制台的票定，PR 里说明理由；两者的已知风险见"后果"。

## 和"方式少而统一"的取舍

产品负责人的最高原则是"凭直觉就会、不用专门学；方式少而统一"（2026-10-16）。这个选择在两边的结果不一样，要说清楚：

- **对用控制台的人**，它满足这条原则：只有一个控制台、一种按法，界面上的"为什么"和"能不能按"都来自服务端，和车载屏、MCP 看到的是同一套判断。
- **对开发、CI 和 AI**，它违背"方式少而统一"：从一种语言、一套包管理、一套测试驱动，变成 C# 加 TypeScript 两种语言，NuGet 加 npm 两套包管理，`dotnet test` 之外再加前端的构建和浏览器测试。AI 会话要多会 npm、TypeScript 和 Playwright，CI 要多装、多跑、多维护一套东西。

为什么仍然值得：这条原则首先是为现场用控制台的人定的，开发这一侧的代价由产品负责人明确接受（"可以引入，目前这个 SIMPLE 项目支持引入"，2026-10-17）。换来的是：控制台没有自己的一套页面片段或界面逻辑，业务判断只在服务端接口里写一次，AI 观察和测试系统仍然只有"服务端接口和事件记录"一个入口；地图这类交互用成熟的库来做，不手写。

## 考虑过的做法

调研于 2026-10-17 读了各方案的官方文档和源码，下面的数字都出自那次调研。

- **服务端出页面、用 htmx 局部刷新，地图单独写一个脚本**：在"不引入 Node"的约束下排第一。轮询无状态、不怕断线，每个页面片段是普通网址、测试能直接打 HTTP，htmx 只有一个文件，直接放进仓库。不选的原因：
  - 网页要另有一套页面片段，等于在服务端接口之外又多了一个出口；
  - 地图的拖动、缩放、动车加断线显示，估计要手写两三百行没有类型检查的脚本；
  - htmx 2 的请求默认永不超时（`htmx.config.timeout = 0`），必须记得改；
  - htmx 4.0.0 已于 2026-08-28 发布、事件改名，用 2.x 以后要迁移一次。
- **Blazor Server（全部用 C# 写界面，服务端为每个打开的页面保持一条 SignalR 长连接）**：只用 C# 一种语言，实时性好。不选的原因是它的默认值和"断线必须马上看得见"相反：
  - 连接半断不断时，要等 30 秒服务端超时才弹出重连框，这期间画面看着是活的、按钮也能按；
  - 服务端只为断开的页面保留 3 分钟；
  - 断开约 6 分钟后浏览器不再重试，一直开着的电脑会停在"重连失败"，要有人点一下。

  断开约 6 分钟这个数，出自 ASP.NET Core `release/10.0` 源码 `src/Components/Web.JS/src/Platform/Circuits/CircuitStartOptions.ts` 的默认值：最多重试 30 次，前 10 次立即、再 10 次每 5 秒、之后每 30 秒，合计约 350 秒。微软文档把默认重试间隔算作实现细节，版本之间可能变。这些能调，但调的正是这个产品最在乎的部分；界面逻辑在服务端那条连接里，没法只靠打 HTTP 测。每个打开的页面约 250 KB 起（微软文档的数字），这个规模下不是问题。放开工具链的约束后，它"只用 C#"的长处不再关键。
- **Blazor WebAssembly**：界面在浏览器里跑 C#，要下载 .NET 运行时；实时通道和断线检测照样要另做，没有比单页应用省事的地方。
- **服务端推送（SSE、SignalR）代替轮询**：推送更及时，但断线检测照样要自己写心跳判断；走明文 HTTP 时，同一个浏览器对同一地址最多 6 个连接、所有标签页共用（MDN）；有的实现断线后重连等待长达 60 秒。每秒一次轮询在这个规模（几个项目、几台到几十台车、几十个标签页）下负担可以忽略。

## 后果

- **多一套工具链**：开发电脑和跑 CI 的机器（现在是 `vm01`，以后还有 `simple01`）都要装 Node 和 npm。往这两台机器上装东西按工作区规矩要先问产品负责人，由实现控制台的票提出。
- **第三方包多**：npm 的依赖要用锁文件锁住版本，版本钉死，定期升级；仓库是公开的，依赖来源要和 .NET 的包一样认真对待。工具链和锁文件的规矩，由实现票写进仓库 `CLAUDE.md`。
- **构建多一步**：前端要先编译成静态文件。`simple up`（一条命令起停本地系统）和 CI 都要包含这一步。
- **Playwright 要装浏览器**：跑 CI 的机器（`vm01`，以后还有 `simple01`）上要装一个无头 Chromium（约 120 MB），同样要先问产品负责人。两种用法各有已知风险：
  - .NET 包：本身约 200 MB，里面自带一个 Node 运行时；官方包 `Microsoft.Playwright.Xunit.v3` 没有声明测过 xunit.v3 4.x 加 Microsoft Testing Platform v2，要实测；在 MTP 下 `.runsettings` 里的 Playwright 配置会被忽略，配置要写在代码或环境变量里。
  - Node 的 `@playwright/test`：用前端项目已有的 Node，但测试结果不在 `dotnet test` 里，CI 要多跑一步、多收一份结果。
- **控制台上厂区网要等接口有鉴权**：按仓库的安全规矩，服务端接口有鉴权之前只监听回环，控制台也就只能在服务端本机打开；登录与鉴权（ADR 0016）做好后才能让厂区网里的电脑用。
- ADR 0016 里"前端框架由实现控制台的票定"由本篇定下。
