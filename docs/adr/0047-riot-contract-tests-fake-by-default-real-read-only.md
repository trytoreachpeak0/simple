# RIoT 契约测试默认只对假 RIoT 跑，对真 RIoT 只由人选定、只读

仓库规则说车队调度系统的行为是契约：在真 RIoT 上观测到的行为写成 `Simple.Contracts.Tests` 里的测试，任何假 RIoT 都要先通过同一批测试。同一份测试既能对假 RIoT 跑，也能对真 RIoT 跑，才能发现假的和真的又不一样了（上一代假 RIoT 对"查无此单"回 404、真 RIoT 回 200，就是没人发现的漂移，见上一代服务端的 `cs#404`、`cs#432`）。但真 RIoT 是全厂共用的生产系统，契约里很多操作会让车动、会下急停，这些按仓库规则每次都要产品负责人单独授权、现场有人。#11 留了一个问题：契约测试怎么在假 RIoT 与真 RIoT 之间切换。本篇回答它（#61）。

**Status**: accepted（2026-10-17，产品负责人确认，原话："确认，CI 绿了就合"）

## 决定

- **默认、CI 上永远只对假 RIoT 跑**：每条契约测试在测试进程里起一个新的假 RIoT（`Simple.FakeRiot`），经 riot-sdk 的 Facade 调它，不开端口，不连任何别的机器。
- **对真 RIoT 跑，只能由人为这一次运行选定**：设环境变量 `SIMPLE_CONTRACTS_RIOT_SETTINGS`，指向一个放在任何 git 克隆之外的 JSON 文件，文件里写端点、调用密钥、一台车和几个站点。仓库里不放任何真实端点或凭据，也没有指向真 RIoT 的默认值或开关。
- **设置文件只确认这一次运行**：文件里必须写 `runUntil`，即这次运行到几点为止；过了这个时刻，或者写得比现在晚 12 小时以上，都拒绝。环境变量留在终端或用户环境里时，之后的运行（包括同一个终端里的 AI 会话）不会因此悄悄连到真 RIoT。
- **拒绝的情形**：`CI=true` 时拒绝，因为 CI 机器在厂区网络里，连得到真实系统；设置文件在任何一个 git 克隆里也拒绝，不只是本仓库，任何上层目录有 `.git` 都算，免得带凭据的文件被提交，经符号链接或目录联接指进克隆的也算；文件缺必需的项时拒绝。拒绝时测试失败并说明原因，不悄悄退回假 RIoT。
- **调用之前先说要调谁**：对真 RIoT 跑时，第一次调用之前，把端点、车和设置文件的位置打到标准错误上。
- **对真 RIoT 只跑只读契约**：鉴权、查单、地图、站点、边表、路线代价。建单、发订单命令、急停、上下线这类契约在真 RIoT 上一律跳过，跳过的理由写明：在真 RIoT 上每一次写操作都要产品负责人逐次授权、现场有人。需要假 RIoT 控制面的契约（代替车旁的人做事，例如让订单挂起）在真 RIoT 上也跳过。跳过算"判断不了"，不算通过。
- **写请求在发出前就被拦下**：跳过靠每条契约自己写，漏写一行就可能在真 RIoT 上建单。所以对真 RIoT 的每个请求都经过一层白名单，只放行契约用到的读接口，逐个列名：读地图、站点、边表、车辆信息、订单详情和订单列表的 GET，以及四个只读的 POST（登录、三个路线查询）。不是"GET 都放行"，因为 RIoT 有会动作的 GET（例如发动作指令 `execActionCommand`、清车并取消订单 `clearVehicleAndCancelOrderTask`）。不在名单上的请求，包括 RIoT 以后新加的接口，都不发出去，测试直接报错。
- 产品负责人说过、但还没在真 RIoT 上测过的行为，测试上标"未在真实 RIoT 上验证"，假 RIoT 照着做；验证另走 #11。

## 后果

- 写操作类的契约（订单生命周期、急停、上下线等）目前只能证明假 RIoT 和实验室记录一致，不能自动发现真 RIoT 在这些地方变了。RIoT 升级后要靠只读契约先发现变化，写操作类的再按授权、有人在现场的方式逐条核对。
- 对真 RIoT 跑一次只读契约，也会给全厂共用的 RIoT 增加一小批读请求。所以只在人选定时跑，不定时、不在 CI 上跑。

## 考虑过的做法

- **CI 上定时对真 RIoT 跑只读契约**：能尽早发现 RIoT 变了；但 CI 机器就要存一把真 RIoT 的调用密钥，而且是在没有人选定的情况下连生产系统。
- **对真 RIoT 也跑写操作类契约，用一个"允许写"的开关**：开关写进设置文件后会一直留着，和"每一次都单独授权"不符；建单还会让车真动起来。
- **用一个环境变量放端点和密钥，不用设置文件**：环境变量容易留在终端里，被后面别的命令带上；设置文件放在克隆之外、每次指一次路径，更清楚这一次连的是谁。
