# 传输用 gRPC，双向加密，每台车载电脑自带钥匙，确认是哪台车时核对配对码

服务端按车载终端报的门锁读数决定放不放车走、要不要下三类急停（ADR 0009）。谁能在厂区 Wi-Fi 上冒充一台车载终端报"全部锁着"，谁就能让一台门没锁的车开走；谁能冒充服务端，就能给车载终端发开锁请求。上一代的 ADR 写的是加密加每车独立密钥，实际做成了明文 TCP 加全车队共用一个凭据，分帧、心跳、重连也都是手写的。厂方对厂区网上的通信没有硬性安全要求（产品负责人 2026-10-16），这一层是我们自己为门锁读数这条安全判据做的。

SIMPLE 服务端只能装在 factory01 上，系统是 Windows Server 2016（产品负责人 2026-10-16）。车载电脑是 Windows 10 专业版 22H2，三台由同一个镜像克隆，机器名和 GUID 相同（ADR 0007）。调研比较了 gRPC、SignalR、MQTT 三种传输，以及双向加密、单向加密加令牌、不加密三种安全做法，产品负责人选了 gRPC 和双向加密（2026-10-16）。这套组合已经由验证票 #18 在开发机回环上、再在 factory01 和 agv03 之间实测跑通（2026-10-17），见文末"验证结果"；两条退路都没有用上。

## 决定

- **传输**：车载终端做客户端，主动连 factory01 上的服务端，一台车同一时刻只有一条 gRPC 双向流，ADR 0024 的两种消息都走这条流。服务端用 Kestrel 自己承载：Windows Server 2016 上的 IIS 和 HTTP.sys 承载不了 gRPC（ASP.NET Core 文档：要 Windows Server 2022 起）。断了由车载终端重连，间隔逐步拉长到上限 25 秒（车载终端程序内置，ADR 0008），现场不用操作。
  - 2026-10-17 按 #18 第 6 步改：原来跟 ADR 0008 的通用上限一样是 30 秒。实测停服务端 60 秒再起来，车载终端恰在服务端起来前后试了一次失败，下一次就在 30 秒后，30.8 秒才重新连上，超过"服务端恢复后 30 秒内重新建流"。上限只要比 30 秒短出一次建连的时间就够，产品负责人选了把上限降到 25 秒、判据不变。其余没有副作用的重试（读 MES、连车队调度系统、读 IO 模块）仍按 ADR 0008 的 30 秒。
- **加密**：TLS 1.2。两台机器都没有 TLS 1.3（Windows 文档：从 Windows 11、Windows Server 2022 起才有）。服务端第一次启动时自己生成一张证书，车载终端只认这一张，它的指纹写在车载终端本机、仓库外的配置里，和服务端地址放在一起。不依赖厂里的证书体系，也不用续期。
  - **服务端的私钥要放在持久的密钥存储里**（2026-10-17 按 #18 补）：Windows 的 TLS 实现 SChannel 不接受只放在内存里的私钥，实测报 `Authentication failed because the platform does not support ephemeral keys.`（内层 `No credentials are available in the security package`）。服务端从证书文件导入时，Windows 会在密钥存储里建一个临时的密钥容器，服务端正常退出、释放证书时删除；进程被强行结束时会留下，所以服务端要正常关停，部署时还要说清这个容器留在哪里、谁清理。
- **每台车载电脑自带钥匙**：车载终端第一次启动时在本机生成自己的钥匙，私钥不离开这台电脑。这把钥匙既是 ADR 0007 说的"认出是哪台车载电脑"的依据，也是它的凭据。车载电脑有 TPM（主板上的安全芯片）的，私钥放进 TPM，整盘克隆也带不走它（产品负责人 2026-10-17）。
  - **钥匙必须由车载终端程序自己在交互登录的会话里生成**（2026-10-17 按 #18 补）：私钥放进当前用户的密钥存储要用这个用户的 DPAPI 主密钥，经 SSH 公钥登录的会话拿不到它，实测在 SSH 会话里建钥匙报 `System.Security.Cryptography.CryptographicException: 拒绝访问。`。车载终端程序以车上的交互登录账号运行时没有这个问题；装车载终端、换电脑、重新生成钥匙都不能靠经 SSH 跑的脚本代办。
  - **这批车载电脑没有 TPM**（2026-10-17 按 #18 补）：agv03 上 `Get-Tpm` 报 `TpmPresent=False`。三台车同一镜像、同一批硬件，按没有 TPM 对待：私钥放在车载电脑的软件密钥存储里，不可导出。下面"后果"里那条接受的风险因此是这批车的常态，靠"两台交替上报就两台都拒并告警"兜底（已实测）。
- **确认是哪台车**（ADR 0007 的那一步，产品负责人 2026-10-16）：
  1. 新装或更换的车载电脑开机连上后，车载屏显示"等待在控制台确认这是哪台车"和一个 6 位配对码；
  2. 控制台的待确认列表里显示同一个码；
  3. 工程师核对两边一致，选"这是哪台车"，服务端从此认这把钥匙。
  确认时要有人看得到车载屏：工程师在车旁打开控制台，或车旁的人把码报给工程师。确认前服务端不用它的上报，也不给它发开锁请求和提问。克隆出来的电脑长得一模一样，光看名字分不出是哪台，所以要核对码。
  - **没登记的钥匙自称某台车**（2026-10-17 按 #18 补，调度确认）：车载终端确认后会在本机记下自己的车辆标识，并在车载上报里带上。服务端没登记过的钥匙如果在上报里自称某台车，服务端直接拒绝这条连接（gRPC 状态 `UNAUTHENTICATED`），不进待确认列表；不自称任何车的才进待确认、显示配对码。车载终端被这样拒绝后，丢掉本机记的车辆标识，下次按新装的车载电脑重新走配对码确认；被控制台删掉登记的车载电脑也是这样回来的。被冒充的那台车照常工作；这时要不要在控制台告警，还没定。
- **同一把钥匙又来一条新连接**：新连接顶替旧连接，旧的那条关掉。Wi-Fi 抖一下、车载终端很快重连，就是这个样子，不能误判成克隆。只有两条连接交替送来新鲜的车载上报（两台电脑真的同时在跑，克隆就是这样），才两台都不接受，在控制台告警，由工程师重新确认（产品负责人 2026-10-17）。同一个车辆标识配在两把不同的钥匙上同时连进来，也一样两台都不接受。所以做车载电脑镜像要用还没确认过的电脑，或者克隆后先清掉新电脑上的钥匙再接入（产品负责人 2026-10-16）。
- **换电脑时，原来那台要么作废钥匙，要么在控制台吊销**：原电脑要继续留作别用的，先删掉它的钥匙；做不到就由工程师在控制台吊销这把钥匙（产品负责人 2026-10-17）。
- 服务端那张证书文件丢了（例如 factory01 重装又没备份），三台车载终端都要重新配置、重新确认，所以它要备份；谁备份、放在哪里，归部署那张票。
- **验证与退路**：验证票 #18 已在 factory01 和 agv03 上跑通（2026-10-17），双向加密和 gRPC 都没有问题。原定的两条退路留作记录：Windows 上的双向加密握手跑不通，就改用单向加密，再加确认时由服务端发给这台车的令牌，现场流程（配对码、选车）不变；gRPC 在 factory01 上跑不通，就把 ADR 0024 的两种消息原样搬到 SignalR（WebSocket）上。

## 考虑过的做法

- **SignalR（WebSocket）**：在 factory01 上也能跑，如果以后控制台网页也用它，推送方式能统一；但消息格式没有独立的定义文件，"加字段不破坏旧版本"要我们自己守。留作 gRPC 跑不通时的退路，验证后没有用上。
- **MQTT**：要多一个中转站程序，要装、要配、要监控，独立的 Mosquitto 能不能在 Windows Server 2016 上跑没有核实；断线重连照样要自己写；它的长处（离线队列、保留消息）在"整份状态"的做法下用不上。
- **继续自己写 TCP**（上一代）：分帧、心跳、重连都要自己写和维护，产品规则要求有成熟库时不手写。
- **单向加密加每车令牌**：没有 Windows 客户端证书那一块不确定，但令牌是"拿到就能用"的凭据，比私钥更容易被不小心写进日志；钥匙和"认出是哪台电脑"的标识也变成两样东西。留作退路，验证后没有用上。
- **不加密**：最省事，但能在厂区 Wi-Fi 上抓包的人就能冒充车载终端伪造门锁读数，或冒充服务端发开锁请求。
- **全车队共用一个凭据**（上一代实际的做法）：分不出是哪台车，一台泄露全部泄露。
- **服务端私钥只放内存**（#18 试过）：不留任何临时密钥容器，但 SChannel 不接受，见"加密"。
- **退避上限保持 30 秒、把判据改成"不超过退避上限加一次建连时间"**（#18 第 6 步）：不用改程序，但现场看到的是"服务端恢复后可能要半分钟多"，产品负责人选了降上限。

## 后果

- factory01 上多一个端口、一个要备份的证书文件；车载电脑上除了车载终端程序和它的配置，不装别的。
- 2026-10-17 按 #18 补：factory01 的厂区网卡和车载电脑的网卡所属的防火墙配置文件都是关着的，所以 SIMPLE 服务端的端口实际上对整个厂区网开放。原来这里写的"一条防火墙规则"在现状下不起作用；要不要打开防火墙配置文件、怎样只放行车载网段，由部署那张票定。服务端只绑 factory01 厂区网卡的地址，不绑 `0.0.0.0`，免得一并暴露到 CI 所在的另一个网段。
- 换车载电脑和第一次装一样，走一次配对码确认；多出的一步是原电脑作废钥匙或在控制台吊销。
- **接受的风险**：私钥没放进 TPM 的车载电脑被整盘克隆、而原机关着时，克隆出来的那台连上来会被当成原来那台车，服务端分不出来；原机一开机，两台交替上报，才会被认出来（产品负责人 2026-10-17）。所以私钥尽量放进 TPM，换下来的电脑一定作废钥匙或吊销。这批车载电脑没有 TPM，这条风险是常态。
- Windows Server 2016 的延长支持 2027-01-13 结束，之后 factory01 上的 .NET 10 也不再算受支持（.NET 支持说明）。车载电脑的 Windows 10 专业版 22H2 已经不在 .NET 10 的支持列表里，这一点早已接受（ADR 0001）。factory01 之后怎么办另议。

## 验证结果（#18，2026-10-17）

验证票用一对一次性的探针程序（`tools/protocol-probe`），先在开发机回环上、再在 factory01（服务端）和 agv03（车载电脑）之间，按 #18 的步骤跑了一遍。逐步的数字、日志原文和清理核对在 #18 的两条结果评论里，原始证据在仓库外。

- **协商结果**：factory01（Windows Server 2016 Standard 14393.9418）上的 Kestrel 以 HTTP/2、TLS 1.2、`TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384`、ALPN `h2` 接受了 agv03（Windows 10 专业版 22H2，19045）用不可导出的 ECDSA P-256 私钥发出的自签客户端证书。服务端证书也是 ECDSA P-256，车载终端只按公钥 SHA-256 钉住它，不看主机名和证书链。车载终端进程启动到建流不到 1 秒。
- **成立的判据**：30 分钟双向流里 1791 份上报零缺口，上报间隔 p99 1021 ms，180 条命令全部回显；服务端 5 分钟不下发、车载终端 9 秒才上报一次，流都不断；静默断链 10 次，服务端每次 9.5～9.7 秒判上报过期，恢复后 0～3.6 秒重新建流、认作同一台；明文连接和换了证书的服务端都被拒绝；配对码两边一致，确认前不用上报；快速重连 10 次全部顶替、不告警；两个进程用同一把钥匙时两边都被拒并告警；吊销立即生效；太新、太旧的大版本以 `FAILED_PRECONDITION` 被拒并按退避重试；双方互带对方不认识的字段，流不断。
- **不成立、已改**：服务端停 60 秒再起来，30.8 秒才重新连上，见"传输"。
- **不适用**：真断 Wi-Fi 那一步。车载终端没有无线网卡，车载电脑经有线接 CPE，由 CPE 走无线入网；真实的断网是 CPE 那一段断，车载电脑的网卡一直连着。改用"连接两头都不关、中间一个字节都不转发"的静默阻断代替。私钥放进 TPM 那一步：agv03 没有 TPM。
- **行驶中的网络卡顿**：验证期间车在跑单，agv03 到 factory01 这段网络卡了约 5 秒，v2 服务端按它自己约 6 秒的静默判断关掉了 agv03 上 v2 车载端的连接；探针的流没有断，卡住的 4 份上报一起迟到，其中 3 份按"最多多久以前写的"被正确判为不新鲜。这就是 ADR 0024 不靠连接断开、靠上报新不新鲜来判断的原因。
- **实测用的配置**：
  - 服务端：Kestrel 只开 HTTP/2，TLS 只开 1.2，要求客户端证书、接受任何自签证书（钥匙对不对由服务端自己的登记判断）；请求体与响应的最低数据速率和空闲超时用默认值，不会掐断低流量的长流。Kestrel 默认不发 HTTP/2 保活 ping：链路静默断掉时，服务端那条流一直挂到链路恢复。这不影响判断（靠上报过期计时器），但要回收死连接就要打开，实测间隔 15 秒、超时 15 秒时约 32 秒回收。
  - 车载终端：HTTP/2 保活 ping 间隔 10 秒、超时 10 秒，约 15～20 秒发现连接已死；连接超时 10 秒；不走系统代理；重连用带抖动的指数退避，1 秒起、上限 25 秒（实测用的是 30 秒，见"传输"）。

需要接着做的：被冒充时要不要告警、待确认列表要不要设上限，转后续票；部署时服务端临时密钥容器的清理、防火墙怎么配、证书备份，归部署那张票。
