# 服务端与车载终端之间只有两种整份状态的消息，车载终端只存身份

上一代服务端与车载端之间约有 65 种消息、六种投递类别，两端各有一个先落盘再发的发件箱，车载端还在本机数据库里存了一份旅程快照和约 25 个字段的恢复状态，于是两边永远要对账。四个仓库约 350 张与协议相关的票里，最多的是状态对不上（约 75 张），其次是可靠投递与去重（约 36 张）；调研的结论是这些大部分来自设计选择，不是业务要求：业务上真正绕不开的只有"开锁是不可撤回的物理动作，同一个开锁不能执行两次"。产品负责人要求凭直觉就会、方式少而统一，消息种类越少越好，信息尽量用状态而不是事件传（2026-10-16）。

产品负责人先定了业务上的边界：车载终端不做任何业务判断，断网时车载屏上什么都不能做（2026-10-16）。在此之上，消息怎么分、开锁和按键怎么不重不迟到，由调研比较了三套方案（两份整份状态；议程原稿的状态上报、编号命令、写盘的人工输入；按键走一问一答），产品负责人选了两份整份状态，仓位与 IO 点位的对应表不下发（2026-10-16）。

## 决定

**断网时现场能做什么**

- 车载终端连不上服务端时（网络断了、服务端停了、车载终端程序被关掉、车载电脑关机或断电、网线被拔），车载屏只显示"与服务端断开"，扫码和所有按钮都不能用，包括停用车上的任意开门（ADR 0011、0012）。车旁的人只能做物理动作：关门、按急停按钮、拨锁上的应急位置开门、取出货物（产品负责人 2026-10-16）。车载终端不记录断网期间人做了什么，也不事后补报。
- 服务端那边照 ADR 0009 处理：门锁读数过期就算门锁未证明锁闭，断联 2 分钟算车载终端故障。AGV 关机时车载终端立即断电（产品负责人 2026-10-16），和断联一样处理，不另立规则。
- 不设单独的"现场处理模式"。要人在车旁处理，就在控制台停用这台车（ADR 0011、0012），车载屏上没有切换模式的按钮（产品负责人 2026-10-16）。

**两种消息**

- **车载上报**（车载终端 → 服务端）：IO 模块每个点的原始值、能不能读到 IO 模块、车旁的人刚做的车旁操作、本次启动执行过哪些开锁请求，以及车载终端的身份和版本。
- **下发状态**（服务端 → 车载终端）：车载屏上显示什么，和现在要执行的开锁请求。
- 两种都是整份发：一有变化立即发，没变化也每秒发一份。丢一份由下一份补上，所以没有单独的心跳、握手、回执、重发和去重表；第一份车载上报和第一份下发状态就是握手。收到一份消息里有看不懂或不合法的单项（例如不存在的点位号），跳过这一项并在下一份消息里说明，不断开连接。
- 车载屏上显示什么全部由服务端用通用的描述决定：文字、带按钮的提问、倒计时、提示。车载终端照着画，不认识业务。给车载屏加一个业务按钮，只改服务端，不加消息，也不用升级车载终端。

**车载终端存什么**

- 车载终端硬盘上只存身份：车辆标识（ADR 0007）、服务端地址、服务端证书指纹和它自己的钥匙（ADR 0025）。不存任务、仓位、编号、发件箱，也不存点位对应表；日志只给人排查，程序从不读回。车载终端随时断电、重启都不会留下要清理或对账的东西。
- **IO 点位对应表**放在服务端车辆清单里（ADR 0017），由管理员在控制台改，只能对停用的车改：车可能正在装货或在路上，表一换，服务端会把好几个仓一下子判成故障，甚至开错门（产品负责人 2026-10-16）。每台车的接线顺序可能不同，所以每台车一份（产品负责人 2026-10-16）。车载终端不拿这张表：它只报每个点的原始值，服务端按表理解；开锁请求直接写要给哪个输出点脉冲。改完表要在停用的车上逐仓开门核对，重新启用前的核对（ADR 0011）再挡一次接错的线。车载终端身份还没确认时（ADR 0007）照样上报原始值，但服务端不用于业务。

**时间不靠车载终端的钟**

- 车载电脑的时钟不可信（主板电池问题，冷启动可能跳一百多天），服务端从不用车载终端报的绝对时间。车载终端只报相对时长：距上次成功读到 IO 模块多久、每个输入点距上次变化多久。
- 每份消息都带自己的序号，和最近收到的对方序号。每一方只用自己的钟，就能算出对方这份消息最多是多久以前写的。ADR 0009 的门锁读数新鲜度按"这份上报最多多久以前写的 + 距上次读到 IO 模块多久"算，不超过 10 秒才新鲜；同一条连接卡住后成批送到的旧上报因此不会被当成新鲜读数。
- 每个输入点上报"本次启动以来变化了几次"。中间丢了几份上报、或断联了一会儿，服务端照样知道门开过、关过几次，ADR 0009、0012 的"跳动""车停着、锁着，光幕却变了"都按它判断。

**开锁请求只执行一次、不迟到**

- 每个开锁请求有唯一标识，只对车载终端这一次启动有效。车载终端记住本次启动见过的开锁请求，执行了或拒绝了都算用掉，再看到就跳过。
- 车载终端收到时，这个开锁请求最多是多久以前写的，如果超过 3 秒（参数配置），就不执行，在上报里报"过期未执行"。
- 断线前发出、还没被报用掉的开锁请求，不带进新的连接。
- C2000 设成了脉冲模式，开锁输出自己回到 0，车载终端只发一次"开"（产品负责人的说法，未实测，已记进 #11）。
- **让车动之前再加一关**：有开锁请求发出不到 3 秒、还没被车载终端报用掉，服务端先不让车动。它和 ADR 0009 的"先证明门锁锁闭"一起，挡住"开锁请求刚发出、门还没来得及弹开"的情况（产品负责人 2026-10-16）。

**车旁操作不重、不迟到、尽量不白按**

- 车旁的人的每次按键或扫码，都绑定它回答的那个屏上提问；一次性的提问只认第一次回答，常驻的按钮（"这个仓有问题"、解除二类急停）同一次按下重复到达只算一次。
- 服务端收到时，这次操作最多是多久以前做的，如果超过 5 秒（参数配置），不采纳：例如人按了解除二类急停后网络卡住、人走开了，不能一分钟后让车突然接着走。
- 为了让人几乎碰不到"按了不算"（产品负责人 2026-10-16）：
  - 车载终端 2 秒（参数配置）没收到新的下发状态，按钮和扫码框先变灰，3 秒（参数配置）显示"与服务端断开"；
  - 人一按，这个按钮立刻显示"处理中"，屏上其余按钮暂时变灰，直到新的下发状态到来；
  - 画面因为事情本身结束而变了（例如离站倒计时正好走完），由新画面说明发生了什么，例如"装货时间已到，车即将离开"；
  - 不另设"刚才的操作没有生效"的提示。
- 断开时车载终端丢掉还没被服务端处理的车旁操作，从不跨连接重发。恢复后屏上还在问的，人再按一次。

**结果不明靠读数判断，不靠回执**

- 重连后，服务端按第一份车载上报判断断线期间发生了什么：当前读数、每个点的变化次数，以及本次启动执行过哪些开锁请求。
- 断线前服务端已知开着的门（开锁请求执行了、门锁报过开），恢复后看到它关好、光幕符合这次操作的预期，按 ADR 0005 的正常装卸算，取货、卸货都一样（产品负责人 2026-10-16）。ADR 0008 说的"重连后读数与记录一致"包括这种情况。
- 断线前关着的门，恢复后光幕却变了，算仓位故障（ADR 0012）。断网期间有人拨应急位置开门取走货物，就是这种情况，走故障处置，由班组长用"取出货物交人工"收尾。
- 车载终端重启过（例如 AGV 关机）的，变化次数和执行记录都没了，只看当前读数：锁开着，就当门开着、等关门；锁着、光幕没变，就当没开过；锁着、光幕变了，算仓位故障。开锁执行后、还没报出去车载电脑就断电，而光幕又变了的，服务端分不清是正常装卸还是有人动过，按仓位故障由人确认；这只在不到一秒的窗口里发生，产品负责人说这种情况不常见（2026-10-16）。
- 扫码通过后开锁请求在路上卡住、超时没执行的，服务端仍在等这扇门时就发一个新的开锁请求，恢复后门自动打开，人不用重新扫码（产品负责人 2026-10-16）。

**断联由服务端按上报新不新鲜判断**

- ADR 0009 的 10 秒、2 分钟都按"多久没收到新鲜的车载上报"计，不靠检测连接断开。连接层的保活只用来回收死掉的连接、触发重连，可以放宽，不像上一代 6 秒判失联、2.5 秒超时就拆会话，那是"几秒一次重连风暴"的一半起因。

## 考虑过的做法

- **议程原稿的三种消息：状态上报、带编号的命令、写盘并重发的人工输入**：写盘的按键重连后才生效，可能是一分钟前按的"解除二类急停"；车载终端重启后算不出这次按键是多久以前的，只能丢掉，写盘就没了意义。跨连接重发的开锁命令可能在车开动后才执行。编号用数据库自增号或本地从 1 编号，换库、重装后会撞号，门不开也不报错。把这些都补上以后，它就是本篇的做法多拆出两种消息、多一个写盘的执行记录。
- **按键走一问一答，每按一次单独问服务端**：每次按键有明确结果，但按键和状态走两条路，多几处容易出错的地方，以后每加一种按钮都会有人想再加一个调用；而且只能用 gRPC。
- **断网时车载屏上还能操作，事后补报**：车载终端就得懂业务、存业务状态，又回到两边对账。
- **把点位对应表发给车载终端，由它按仓整理后上报**：两边要对齐"现在用的是哪一版表"，切换时读数作废；不下发就没有这件事。
- **把执行过的开锁请求写进车载终端硬盘**：只多解决"开锁后不到一秒车载电脑断电"这个窗口，产品负责人说不常见；代价是多一个要处理损坏和清理的文件。
- **按键迟到多久都算**：人按了解除二类急停，网络卡住，人走开了，一分钟后车突然接着走。
- **服务端不采纳时，屏上提示"刚才的操作没有生效"**：点了不算本身就很奇怪（产品负责人 2026-10-16），改成网络不好时先让按钮变灰，几乎碰不到。
- **设一个只能在车上切换的现场处理模式**（参照半导体设备的本地／远程模式）：和停用车做的是同一件事，多一种状态和一个按钮。
- **车载终端启动时先把所有开锁输出置 0**：C2000 已设成脉冲模式，输出自己回到 0（产品负责人 2026-10-16）。

## 后果

- 协议管道两端合计估计两三千行，上一代约三万多行。
- 车旁的人偶尔要再按一次：按下的那一瞬间网络卡住超过 3 秒、屏幕显示过断开时。
- 开锁执行后不到一秒车载电脑断电、光幕又变了的，要班组长经故障处置确认。
- 给车载屏加一个按钮（例如待定的"立即出发"）不用改协议、不用升级车载终端。
