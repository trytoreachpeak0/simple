# 参数配置存在服务端，控制台和 MCP 共用同一套修改步骤；不单设受理开关

参数配置就是厂区配置：车辆清单（车辆标识、对应车队调度系统里的哪台车、仓位分组、属于哪个项目）、项目和派车区、区域号归哪个派车区、开门侧、不服务的区域号、每个项目每个任务类型的开关，以及各篇 ADR 里放进厂区配置的时长和次数。上一代这些靠脚本、导入、手改文件再重启来改，是最常出错的地方：改的地方多、没有统一校验、重装还会把改过的值静默写回去。产品负责人不要在仓库里改文件再部署，而要在控制台上改，也要能让 AI 通过 MCP 改（2026-10-16）。仓库规则已定 MCP 只是服务端 API 上的薄壳、自己不带逻辑，所以把修改做成服务端 API 的一个功能，控制台和 MCP 就是同一个功能的两个入口，规矩只写一遍。

## 决定

- **配置存在服务端**，以服务端里的为准。仓库里的 `sites/<厂区>/` 改为起始配置：第一次安装时导进服务端，测试和场景也用它。端点和凭据仍不在其中，照旧从仓库外提供。
- **只能经服务端 API 改**，控制台和 MCP 是两个入口；只有管理员能改（ADR 0014），经 MCP 时也用管理员账号（ADR 0016）。每次修改，不论从哪个入口来，都走同一套步骤：
  1. 给出改前改后的对比；
  2. 服务端对改后的整份配置校验，不通过就不能提交，并说明哪里不对，例如同一个区域号归到两个派车区（ADR 0015）；
  3. 人确认后立即生效，不用重启；
  4. 每次修改存成一个版本，记进事件记录（ADR 0019），能一键退回上一个版本，退回也走这套步骤。
- **只影响之后的新需求**：已经分给车的任务照原来的配置做完，不改派（ADR 0003 对"改配置让另一台车接某类任务"已经这样定，这里推广到全部配置）。
- 控制台上所有登录的账号都能看当前生效的配置（ADR 0014）。
- **不单设受理开关**（产品负责人 2026-10-16）。上一代停止受理是靠"导入一张空表"的副作用实现的，出过多受理一条真实需求的事；SIMPLE 里要停送已经有三条路，不另加第四条：
  - 停一台机台：配置里把它的区域号设为不服务（ADR 0002）；
  - 停一类任务：配置里关掉这个项目的这个任务类型；
  - 停一台车或一个项目的车：停用车（ADR 0011），班组长就能做；车上有货的等它送完。

  前两条只有管理员能做；班组长要停，就停用车。

## 考虑过的做法

- **配置只在仓库里改，走 PR 和部署，控制台只读**：修改记录、审查、回退都是现成的，但改一个时长也要走 PR 和部署；产品负责人要在控制台和经 AI 改。
- **控制台和 MCP 各有一套修改逻辑**：同一件事两套规矩，迟早不一致；仓库规则也不许 MCP 带自己的逻辑。
- **改了配置，已分配的任务也按新配置重排**：会出现改派，与 ADR 0003 相反。
- **单设一个受理开关**（全局、按派车区、按任务类型）：多一条停送的路，还要另定它和配置、车辆启用谁优先。
- **停机台、停任务类型也让班组长做**：这两样是配置，放给班组长就要在配置里再分"谁能改哪几项"。
