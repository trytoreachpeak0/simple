# 事件记录只有一份，审计和运行日志都是它；统计从它算，每日数字长期保存

前几场的 ADR 通篇说"记进事件记录"；客户技术协议另外要求"运行日志记录与统计功能"；控制台有了账号，又要能查"谁在什么时候按了什么"。做成审计、运行日志、事件记录三套，就要定每件事记在哪一套、三套对不上时信哪一套。查问题时最常要的恰恰是把"谁按的"和"服务端那一刻做了什么"放在一起看，例如"班组长按了继续，车却没走"；仓库规则也把服务端 API 和事件记录定为 AI 唯一的观察面。所以只做一份（产品负责人 2026-10-16）。

## 决定

- **事件记录**记下服务端经历的每一次状态变化、服务端的决定和人的动作：什么时候、哪台车或哪条任务、发生了什么、是谁做的。"谁"写到账号为止（哪个项目的哪个角色账号，或管理员，ADR 0016），连同入口：控制台、MCP、车载终端（不带账号，ADR 0005），或服务端自己。客户要的运行日志就是它，查谁按了什么也是查它。
- **只记变化，不记周期读数**：例如"3 号仓的锁从锁着变成开""服务端决定下三类急停""A 项目班组长账号经控制台按了继续"，不记门锁、光幕每一次周期上报的读数，免得记录被淹没。
- **保存期限**放在厂区配置里，默认 180 天（沿用上一代需求基线对服务端审计留存的要求）。程序自己的调试日志不算事件记录，照常另写。（已定，见 ADR 0034：程序日志收进 factory01 上的 Seq，保存 30 天，经服务端读。）
- 控制台按车、按任务、按账号、按时间筛选事件记录；本项目的账号只看本项目的（ADR 0015）。
- **统计**从事件记录算，按车、按项目，按天或按一段时间看。第一版做这 8 项（产品负责人 2026-10-16）：
  1. 送达的任务数和跑了多少趟；
  2. 送达的花篮数；
  3. 从需求出现（MES 网关第一次看到它）到送达用了多久；
  4. 没送达就结束的任务数，按结局分（ADR 0003、0005、0012：故障货物交接、控制台放弃、操作员取消、站点超时）；站点超时的，另分出"当时需求已不在 MES 里"的那部分（ADR 0021）；
  5. 机器人没接、在受理前就从 MES 消失的需求数（多半被人工先送走了，ADR 0003），和送达数一比，就是机器人承担了多大比例的运送；
  6. 每台车的时间花在哪：跑一趟、充电、空闲返回、空闲、停用、故障中，各占多少；
  7. 故障次数，和每次从出现到结束用了多久（车被停用的，算到停用那一刻，ADR 0012）；
  8. 人介入的次数：告警次数，人在控制台或车载终端上按处置按钮的次数。
- **每日统计数字单独保存**，不随事件记录过期删除，以便看半年、一年前的对比。
- 客户验收列的 MTBA、MTBF、MTTA、MTTR、MTTC 等指标，第 7、8 项是计算它们的原料；每个指标的确切口径（什么算一次故障、从什么时候算起、算不算外部故障）要先和客户对过定义，再加进统计。

## 考虑过的做法

- **审计和运行日志分开**：审计可以单独存得更久、单独保护，运行日志可以早清；但两处要对照着查，统计要定从哪套算，AI 要学两个地方。客户只要求运行日志和统计，第一版也只有几台车，这个好处用不上。
- **周期读数也进事件记录**：量太大，要看的变化被淹没；排查读数问题看调试日志。
- **统计另记一套计数**：会出现"日志里 10 次故障、统计里 8 次"。
- **事件记录过期后统计也跟着没了**：看不了长期对比；每日数字量很小，可以一直留着。
- **第一版就按客户验收指标出数**：口径没和客户对过，算出来的数不一定是客户要的。
